| 006 | Where does the app find the program, and when does it download? | Order: the copy that the app downloaded, then a path in `ROBOT_CLAUDE_BIN` or `ROBOT_CODEX_BIN` (which stops the search of the computer), then the PATH and the usual folders. A copy of the data folder on another computer finds the file broken and offers the download again. |
| 006 | What counts as connected for a subscription account? | The program is on the computer, and its sign-in is a subscription (Claude plan or ChatGPT plan). | 006 | What does "Disconnect" do to a subscription account? | It switches the account off in the app only. The vendor program stays signed in, because other tools of the user use it. "Connect again" checks the program and switches the account on. After an import the account is off. |

| 006 | Does a runtime keep a session between turns? | No. Each turn starts a new program run and gets the chat so far as text (the newest 60 000 characters of history, and the new message). Sessions of the program are not saved, so the history of the user's own Claude Code is not touched. |
| 006 | What does the usage page show for a subscription? | The tokens of each reply, as for API accounts. | 007 | How do the permission levels reach Claude Code? | The program asks the app before each step it does not do on its own, and the app answers by the level, in the same cards as the own tools: "Ask for everything" asks for every such step; "Ask for risky steps" asks only when the rules of 007 call the step risky (shell commands by the risk list, files outside the workspace); "Full access" asks nothing. "Always allow" is kept per agent. The question tool of Claude Code is off; the agent asks in its reply. |
| 007 | How do the permission levels reach Codex? | A non-interactive Codex run cannot ask. The level becomes the sandbox of the run: "Ask for everything" is read-only (the agent can look but not change), "Ask for risky steps" is write inside the workspace only (no network, no outside writes), "Full access" has no limit. Approval cards for Codex need its app-server protocol, which is marked experimental by the vendor; they come later. |
| 008 | Can a runtime agent save memory? | It reads the memory items in its instructions, but it has no tool to save one in this version. |
| 004 | Do runtime agents work in channels? | Yes, as members. The lead's plan and summary turns run with no tools, which for Claude Code removes its tools, and for Codex makes the run read-only. |
| 006 | How does Muse Code run, and how does the user sign in? | `muse exec --json` with the prompt in a temporary file and the workspace of the agent. The app sets `MUSE_NO_AUTO_UPDATE=1`, so the launcher does not update itself during a turn, and passes the flags that keep the user's session log and the files of other agent tools out. Sign-in is `muse login` (device code): the app shows the page and the code from the program and opens the page when its host is `meta.com`, `facebook.com` or `meta.ai` over https. The state and the plan limits come from `muse usage --json`, which makes no model turn. A key in `META_API_KEY` is removed from the environment; a key stored in the program is shown as "not a subscription". The app does not download Muse Code: the program is the vendor's launcher, which updates itself, and the app has no published checksum for it. |
| 007 | How do the permission levels reach Muse Code? | A headless run cannot ask. "Ask for everything" turns off write and shell. "Ask for risky steps" keeps the sandbox of the program on. "Full access" turns off the approval and the sandbox. A run without tools turns off write, shell and web tools. |
| 006 | How does pi run, and what counts as signed in? | `pi -p --mode json --no-session`, with the prompt on stdin, and without context files, skills, prompt templates and MCP of the user. pi has no single account: each of its models has its own login or key, which the user sets up inside pi. So the app does not sign in for pi; it offers the models that `pi --list-models` shows, and "signed in" means that the list is not empty. The model id is `provider/model`. The environment of pi is left as it is, because pi can use keys from it; so pi is the one runtime that can bill an API key, and the form says so. The app does not download pi: it is an npm package. |
| 007 | How do the permission levels reach pi? | pi does not ask before a step. The level becomes the list of tools: "Ask for everything" gives read, grep, find, ls; "Ask for risky steps" adds edit and write but no shell; "Full access" gives all tools. A run without tools has none. |
| 006 | Which models do Muse Code and pi offer? | Muse Code offers "Default", which is the model that the program chooses for the account. pi offers the list of its own models and the effort levels that the list marks with thinking. |
| 012 | Which well-known protocols protect the pairing and the later connections? | Pairing: SPAKE2 as in RFC 9382 (curve P-256, SHA-256, HKDF, HMAC key confirmation), from `@noble/curves` (MIT), with the 6-digit code stretched by scrypt (N = 2^15) into the password. A wrong code never shows the code, and 5 wrong tries end the code. Linked connections: Noise `IK` with `25519_AESGCM_SHA256` (Noise specification, revision 34): each side knows the public key of the other from the pairing, so the first message already hides the device. The app checks both against the published test vectors (RFC 9382; the public Noise vector set). AES-GCM is chosen over ChaCha20-Poly1305 because the test runtime of the project does not have the second one. The transport is a web socket; the app seals every message itself, so the link is safe also on a network without TLS. |
| 012 | Where does a device keep its identity, and what does the device id show? | The identity is an X25519 key pair; the private key is in the keychain (the same store as provider keys). The device id is the first 32 hex digits of the SHA-256 of the public key. If the keychain has no key (new computer, or the user cleared it), the app makes a new key and removes all links, because the old links cannot work any more; the user pairs again. |
| 012 | Which port does "Let other devices connect" open? | 47800. If it is taken (a second copy of the app), the app takes a free port and remembers it, so the addresses of the pairing screen are right. The port is the one in the addresses; a typed address without a port uses 47800. Nothing listens while the switch is off. |
| 012 | What is the text of the link that "Copy link" and the QR code hold? | `robot://pair?code=<6 digits>&name=<computer name>&a=<address>` with one `a` for each address. It holds only what the pairing screen shows; the code works once and ends in 5 minutes. |
| 012 | How long does the user of the server have to answer "Allow <name>?" | 2 minutes. After that the request counts as Deny and the joining device sees the plain line "The other computer did not allow this device." The app brings its window to the front when a request comes in. When more than one device waits, the oldest shows first. |
| 012 | What does "Pair a device" do while "Let other devices connect" is off? | It first asks "Turn on “Let other devices connect”?" with the text that a paired device can direct the agents, and turns the switch on only after the user confirms. The two-way answer "yes" in "Connect to a computer" also turns the switch on, and the question says so. |
| 012 | In which order does the pairing screen list the addresses? | Local network addresses first (IPv4), then VPN addresses, then IPv6, at most 8. An address counts as VPN when the interface is named like a VPN (`utun`, `tun`, `tap`, `wg`, `tailscale`, `zt`, `ppp`) or it is in the Tailscale ranges. The screen marks each one "Local network" or "VPN". |
| 012 | What can the user type to change the addresses of a server? | One address on each line, as `host`, `host:port`, `[v6]` or `[v6]:port`. The app tries them in that order. A line that is not an address gives "This is not an address" and saves nothing. |
| 012 | What happens when the same device pairs again, and at the limit? | Pairing the same device again replaces its old link, so it does not count twice. At 10 devices that can open this computer, or 10 computers that this device can open, the new pairing gets "The limit of 10 linked devices is reached." and nothing is stored. |
| 012 | Can a phone be the computer that a client opens? | No. The wire protocol carries the device kind (`computer` or `phone`). A computer only accepts a `computer` as the server in "Connect to a computer"; the pairing screen of a computer is the only way to become a server. A phone is always the client. |
| 012 | How does a client open a place of a linked server, if ids and lists are asked in the same way as on this computer? | The window sends the id of the server on screen with each call that a client may make (the list in 012, “What a client can do”). The main process sends it over the link when that id is a linked server, and runs it here when the id is this computer. The server answers with the same handlers as for its own window, with the linked device as the actor. Any other method from a client gets “Not allowed”, also when the window sends it. |
| 012 | How does a client send files, when it cannot know a path on the server? | The client uploads each file in pieces of 192 KB and gets a token for it; “send message” carries the tokens, and the server maps a token to the stored file. A path is never accepted from a client. A stored file waits at most 15 minutes, is removed after the message used it or when the connection closes, and one device holds at most 10 open files of at most 20 MB each (the limits of a local attachment, 004). |
| 012 | Which files can a client download, and how? | A file in the `attachments` folder of the agent, named in a message of that agent (a name without folders; a link that leaves the folder is refused). The client asks where to save it, with the “Save as” dialog of the system, and pulls the file in pieces. The download button shows on the file chip on a linked server only, and is off while the server is offline. |
| 012 | What does the client cache hold, and where does it live? | The last answers to reads (places, agents, channels, tasks) and the newest 200 messages of each place that was opened while the server was online; messages that arrive live are added to the entry of an opened place. It is kept in a folder `link-cache` in the data folder, apart from the database, so an export never holds it (014). Entries are written in a batch, because a reply streams with an event every 50 ms. The folder of a server is deleted when the link ends, and when the server says “Not allowed”. A place that was never opened shows nothing while the server is offline. |
| 012 | When does a tile show Reconnecting, and when Offline? | A server that was online and loses its connection shows Reconnecting for 3 tries (the waits double from 0.5 s up to 30 s), then Offline; the app goes on trying with the same back-off. A server that was not online since the app started shows Connecting, and then Offline after the first try that fails. The line for the state (“Reconnecting”, “Offline”, “Pair again”, “Update the app”) shows in a strip above the conversation; the tile itself shows a mark and a short name in its label. |
| 012 | What does “Pair again” on a tile do? | It opens the same “Connect to a computer” dialog as the add button. A link that was removed by the server stays in the list of Settings > Devices until the user removes it, so the user can see what happened; its cache is already gone. |
| 012 | Where does “from <device name>” show? | On every message that came from another linked device, on the server and on the other clients, as a small muted line under the text. | 012 | What do a client's page buttons and controls do for what a client cannot do? | Workflows and Usage show the muted line “Open this on <server name>.” Tasks works but has no Retry (a client may stop a task). | 014 | Is the data of a link part of an export? | No. The export removes the `device_link` table from its copy of the database (no device keys or addresses leave the computer), and the client cache is a separate folder that an export does not read. |
| 012 | How does a computer find another one that shows a pairing code? | With the standard multicast name service of the local network (service type `_robot-link._tcp`, IPv4 only), so no service of ours is used. The user picks a computer from the list, and the address field fills; the user still types the code. A computer does not list itself. A name from the network is shown after its control characters are removed and it is cut to 60 characters. |
| 012 | Can a false entry in the nearby list harm the user? | No: any device on the network can announce a name, but pairing needs the code that the real computer shows, and the link keys are checked in the pairing (SPAKE2), so a false computer cannot finish a pairing. | 012 | Can a client choose “Always allow for this agent” on an approval card? | No. A client does not change what an agent may do (007), and an “always” rule lasts after the answer. | 016 | How does the app tell that two changes were made while the computers were apart? | A change counts as made apart when the other computer had not seen it yet when it made its own. For data that existed before the first sync, only edits after the end of an earlier sync count. |

| 016 | Which tasks of the other computer make a task of the same agent wait? | A task that runs or waits for the user (an approval or a question). | 016 | Two computers start a task for one agent at the same moment. Which one waits? | Neither: there is no lock between two computers, so both can run. The rule holds from the moment the state of the first task has reached the second computer (about a second). |

So a clock that is wrong by any amount does not change the result. |
